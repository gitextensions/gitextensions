# ParityInventory

`ParityInventory` is a temporary, cross-platform source-analysis tool for the Avalonia parity
work. It compares an original C# type with its twin and writes deterministic
`functional-findings.json` evidence. It does not belong to either solution.

```powershell
dotnet run --project eng/tools/ParityInventory -- compare `
  --original-root src/app/GitUI `
  --twin-root src/app/GitUI.Avalonia `
  --type GitUI.FileStatusList `
  --translations src/app/GitUI/Translation/English.xlf `
  --framework-adaptations eng/avalonia/framework-adaptations.json `
  --output eng/avalonia/parity-evidence/P0.4/functional-findings.json
```

The report schema version is `5`. It contains:

- deterministic original and twin inventories: source partials, members and lexical order,
  event handlers/wiring, menu trees, hotkey command IDs, settings reads/writes,
  `TranslationString` fields, inferred translation keys with English-catalog presence, and
  normalized C# comments anchored to the member and placement they describe;
- categorized, stable-code findings for missing/extra facts and member-order differences;
- AXAML `x:Name` declarations projected as the private fields generated by the markup compiler,
  so they match same-named Designer fields. Framework-forced control type changes remain
  signature findings, while generated markup-field order is not compared with explicit C#
  declaration order;
- direct WinForms/Avalonia lifecycle event equivalents (`SelectedIndexChanged`/
  `SelectionChanged`, `Resize`/`SizeChanged`, `Enter`/`GotFocus`, and `Leave`/`LostFocus`)
  compared by their shared semantic event without hiding handler or target differences;
- event subscriptions are accepted only when the right-hand side is a lambda, delegate
  construction/cast, local method, delegate-typed value, member handler, or conventional
  handler name; arithmetic, string, coordinate, and other ordinary `+=` assignments never
  enter event evidence;
- explicit `AddTranslationItem` calls with literal or `nameof` item names, `Text` or
  `HeaderText` properties, and an explicit empty source enter the same `.Text` translation
  evidence as empty WinForms Designer assignments. This preserves that identity without
  mutating runtime control text during attachment; ordinary runtime registrations stay out;
- WinForms-shaped Avalonia menu controls (`ToolStripMenuItem`, `ToolStripSeparator`, and
  `ContextMenuStrip`) read from AXAML as native menu entries. Menu children are sequence-aligned,
  so one genuine insertion or omission remains one finding instead of shifting every later item;
- signature comparison ignores formatter-only spaces immediately inside parameter lists while
  retaining parameter types, names, defaults, order, accessibility, and framework type changes;
- `comment.missing`, `comment.changed`, and `comment.drifted` findings. Comment sequence
  alignment prevents one deletion from producing a cascade of false changes;
- a separate `adaptedComments` collection for conservative WinForms-to-Avalonia framework-name
  substitutions. Adaptations remain visible evidence but do not count as parity gaps;
- a separate `acceptedFrameworkDeviations` collection for individually identified shell facts
  supplied by compiled AXAML or `Window.OnClosed`: the WinForms `components` container,
  generated `InitializeComponent`, the `Dispose(bool)` lifecycle boundary, and only the exact
  Designer-generated summary/separator/control-name comments. Each entry retains its original
  path/value, twin part, and rationale. A handwritten TODO, NOTE, HACK, issue link, or any other
  comment inside `InitializeComponent` remains a finding;
- optional reviewed framework adaptations loaded from an explicit manifest. This channel accepts
  exact member and native event facts and pins the type name, finding code/path, every applicable
  source part/value, declared accessibility, full signature, and a non-empty rationale. It has no
  wildcard syntax. A removed finding,
  renamed member, moved partial, or changed signature makes the run fail as stale instead of
  silently accepting drift. Accepted entries remain in `acceptedFrameworkDeviations`; they do not
  establish exact structural identity;
- explicit `partial.missing` findings that name both the original partial and expected twin
  path.

XML documentation, single-line comments, block comments, TODO/HACK/NOTE text, and issue links
are all included. Whitespace and comment delimiters are normalized; text is not otherwise
discarded. AXAML comments are not treated as substitutes for C# reasoning because they cannot
be anchored to an original code member.

Reviewed handwritten comments use the existing schema-4 manifest with additional exact fields. Read
the original and twin methods first. If the code exists, place its comment verbatim, changing only
what would otherwise be false. If it moved, place the comment beside that code and pin `codeMoved`.
Use `codeAbsent` only after checking the whole twin type, including every partial. These entries are
accepted differences, never closed findings or proof of behavior parity.

```json
{
  "schemaVersion": 4,
  "deviations": [
    {
      "typeName": "Sample.Widget",
      "category": "comments",
      "code": "comment.missing",
      "path": "comment/Widget.cs/method:Render()/body/0",
      "originalPart": "Widget.cs",
      "originalValue": "Preserve the native rendering workaround.",
      "reason": "codeAbsent",
      "rationale": "Reviewed every partial: the native rendering operation is absent."
    },
    {
      "typeName": "Sample.Widget",
      "category": "comments",
      "code": "comment.drifted",
      "path": "comment/Widget.cs/method:Update()/body/0",
      "originalPart": "Widget.cs",
      "originalValue": "Save before refreshing.",
      "twinValue": "Save before refreshing.",
      "twinPart": "Widget.cs",
      "reason": "codeMoved",
      "targetMember": "method:Refresh()",
      "rationale": "The save operation and its comment now live in Refresh."
    }
  ]
}
```

Copy the exact finding code/path/value and original part from a fresh report. Both reasons accept
`comment.missing` or `comment.drifted`, including handwritten comments in Designer files. `codeAbsent`
has no twin part or destination fields; a surviving stray comment is still pinned by `twinValue`.
`codeMoved` requires the actual twin part and exact comment anchor as `targetMember`. It also
requires one live comment there matching `originalValue`, or optional `targetText` when a minimum wording
adaptation is necessary. `twinValue` still pins the finding itself: absent for missing, the original text
for drifted. Source text, part, finding or destination drift fails the run; removed findings and unused
pins fail as before. Unreasoned handwritten comments and `comment.changed` cannot be accepted this way.
The dashboard reports these separately by reason and stores their accepted count in measurement history.

The analyzer is deliberately syntax based. It enumerates top-level classes, structs, and
interfaces. Facts that cannot be represented safely become findings rather than
guessed semantic matches. Only `Items`/`DropDownItems` mutations on fields declared as menu
types enter the menu inventory; ordinary list and combo-box item collections do not.
